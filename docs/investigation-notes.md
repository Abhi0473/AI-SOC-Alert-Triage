## Documented failure case: false positive (Scenario 3)

**What happened:** `ALERT-EVT-1003` (host `WIN-SRV01`, user `svc_admin`) is a
legitimate nightly backup script, launched by Task Scheduler, that happens to
use `-enc` for reliable argument passing. The system incorrectly escalated it
— risk score 65 ("high" severity) — because:
1. It matched the same `-enc` pattern as a genuinely malicious encoded
   PowerShell command (`+30` base, `+20` encoded-PowerShell).
2. It's flagged `critical_asset: true` (`+15`), since it runs on a backup
   server.

**Why this happened:** The `suspicious_encoded_powershell` rule is
intentionally simplistic (see `detection-rules.md`) — it has no allowlist for
known-good automation such as scripts launched by Task Scheduler under a
service account.

**What this proves:** Deterministic rules alone are not sufficient, and human
analyst review remains necessary before any alert like this is closed or
escalated for real. A real analyst would notice the parent process
(`taskeng.exe`, not a user shell), the off-hours-but-scheduled timestamp, and
the internal-only destination IP, and downgrade this to `false_positive` in
the dashboard's persisted analyst-verdict field.

## Correctly handled edge case: unconfirmed reputation (Scenario 6)

`EVT-1006` connects to an IP with zero threat-intel history — not confirmed
malicious, not confirmed clean. Earlier versions of this pipeline treated
"no data" the same as "confirmed clean" and generated no alert at all, which
hides a real gap: an analyst has no way to tell the difference between "we
checked and it's fine" and "we never checked." The dedicated
`unconfirmed_reputation_outbound` rule now surfaces this as a **low**-severity
alert (score 10 — well below the "high" severity a confirmed-malicious IP
would produce), and the AI layer correctly recommends `close_as_benign` with
medium confidence rather than escalating on data that doesn't warrant it.
This is the kind of nuance ("don't treat absence of evidence as evidence of
absence, but also don't over-escalate on it") worth raising directly in an
interview.

## Correctly handled true negatives (Scenarios 4 & 5)

`EVT-1004` (ordinary browsing to a known-clean IP) and `EVT-1005` (plain,
non-encoded PowerShell used interactively) both correctly generate **no
alert at all** — the detection layer doesn't fire on either, and they're
counted as true negatives in the evaluation report rather than being silently
excluded from the metrics (a gap in the original V1 evaluation script).

## Possible V1.1 fix for the false positive (not yet built, deliberately)

Add a small allowlist of known parent-process + script-hash combinations that
suppresses or downgrades the Scenario 3 pattern — while keeping the
underlying rule broad enough to still catch a real attacker abusing Task
Scheduler for persistence. That precision/recall trade-off is itself worth
raising in an interview.
